# Phase 3 Spec: People & Tag Enrichment + Metadata Plugins

**Status**: Draft (Future)  
**Phase**: 3 of 3  
**Depends on**: Phase 2 complete. Plugin architecture is now **decided** — see the dedicated [Metadata Source Plugins spec (F22)](metadata-plugins.md) + [ADR-033](../architecture/ADR-033-metadata-source-plugins.md) (sidecar providers over a unified resolution layer). Writeback strategy (safe edit-back to source files, F17) remains a **future ADR**, designed to consume the F22 shadow layer.

---

## Objective

Extend the People and Tags data models to support rich metadata, aliases, and graphs. Add an external metadata plugin system (IMDB, TMDB). Enable metadata writeback to source files.

---

## Scope

### In Scope
- People: aliases, configurable extra metadata fields (birthdate, website, etc.), profile images
- Tags: aliases, parent/child hierarchy (tag graph), tag images
- External metadata plugin interface (IMDB, TMDB)
- Metadata edit UI with writeback to source MP4/MKV files
- Autogenerated video preview trailers

### Out of Scope (Phase 3)
- Multi-user support
- Cloud storage backends
- Video uploads

## Functional Requirements

### F14: People Enrichment

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F14.1 | A Person record supports N aliases; any alias matches in search and filter | Adding alias "Rob" to "Robert Smith" causes videos tagged "Rob" to surface when filtering by "Robert Smith" |
| F14.2 | Configurable extra metadata fields per Person via a JSON schema defined in app config (e.g., `birthdate`, `website`, `nationality`) | Config file declares fields; UI renders them on person detail page |
| F14.3 | Person profile image stored at `DATABASE_PATH/images/people/:person_id.{jpg,png}` | Uploading an image via UI stores it and displays it on the person's page and index card |
| F14.4 | Person detail page displays all enrichment fields alongside video list | All configured fields visible |
| F14.5 | MCP `list_people` and `get_person` tools return alias and extra metadata fields | Verified via MCP tool call |

### F15: Tag Enrichment

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F15.1 | A Tag supports N aliases; alias lookup resolves to canonical tag | `football` and `soccer` both resolve to the same tag when one is set as alias of the other |
| F15.2 | Tags support a parent relationship (directed acyclic graph); querying a parent tag includes all descendant tags | Filtering by `sport` returns videos tagged `football`, `basketball`, `tennis` if those are children of `sport` |
| F15.3 | Tag images stored at `DATABASE_PATH/images/tags/:tag_id.{jpg,png}` | Image displayed on tag index card and detail page |
| F15.4 | Tag graph UI: a visual representation of tag hierarchy on the `/tags` page (optional, can be a tree list) | Tag hierarchy is navigable in the UI |
| F15.5 | MCP `list_tags` returns alias and parent/child relationships | Verified via MCP tool call |

### F16: Metadata Source Plugins

> **Detailed and made concrete in the [Metadata Source Plugins spec (F22)](metadata-plugins.md) + [ADR-033](../architecture/ADR-033-metadata-source-plugins.md).** Decisions locked: providers are **sidecar containers** speaking a small HTTP contract; **People** is the v1 slice; matching is **embedded-ID-first with a name-search fallback**; provider data is a shadow layer merged through ADR-013's precedence model. The high-level F16 table below is retained for roadmap context.

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F16.1 | Plugin interface defined in config: each plugin specifies a source (IMDB, TMDB, custom URL), API key env var, and field mapping | Config file with a TMDB plugin entry is loaded on startup |
| F16.2 | Videos with an embedded IMDB ID (`©imdb` atom or MKV `IMDB` tag) can be enriched from the configured plugin | Clicking "Fetch from TMDB" on a detail page populates title, tags, people from TMDB |
| F16.3 | Enrichment is always manual/on-demand — never automatic | No background enrichment job runs without user initiation |
| F16.4 | Plugin data is stored in a shadow layer separate from file-sourced metadata; the two are displayed distinctly in the UI | UI labels enriched fields as "from TMDB" vs. "from file" |
| F16.5 | Enrichment data is writable back to the source file if the user explicitly requests it (see F17) | Button "Write plugin data to file" triggers writeback |

### F17: Metadata Writeback

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F17.1 | Edit any metadata field (title, people, tags, date) in the video detail UI | Form on detail page allows editing all fields |
| F17.2 | On save, write changes back to the source file's embedded tags using ffmpeg (MP4) or mkvpropedit (MKV) | File's embedded metadata updated; re-scan confirms changes are read back correctly |
| F17.3 | Before writing, create a backup copy of the original file at `DATABASE_PATH/backups/:filename.bak` | Backup file exists after first writeback |
| F17.4 | Writeback is explicitly opt-in: a "Write to file" button distinct from "Save to database" | Two distinct actions; saving to DB does not touch the file |
| F17.5 | `WRITEBACK_ENABLED` env var (default: `false`) must be set to `true` to enable the feature | UI hides write-to-file controls when disabled |

### F18: Autogenerated Preview Trailers

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F18.1 | Background worker generates a 20-second preview clip per video by sampling frames across the duration | Preview clip file stored at `DATABASE_PATH/previews/:video_id.mp4` |
| F18.2 | Preview plays on hover over the video card in the browse view | Hovering a card for > 500ms starts autoplay of the preview (muted) |
| F18.3 | Preview generation is opt-in via `PREVIEW_ENABLED=true` env var | Disabled by default; no generation without opt-in |
| F18.4 | Preview generation can be triggered per-video via `POST /api/media/:id/preview` | API call triggers generation; 202 Accepted returned |

## Data Model Extensions (Phase 3)

```
PersonAlias
  id          PK
  person_id → Person
  alias       string

PersonMetadata  (key-value for configurable fields)
  person_id → Person
  key         string
  value       string

TagAlias
  id          PK
  tag_id → Tag
  alias       string

TagParent   (directed graph edge)
  child_tag_id  → Tag
  parent_tag_id → Tag

MetadataPlugin  (config-driven, stored for reference)
  id          PK
  name        string
  source_type enum (IMDB, TMDB, custom)
  config_json JSON

VideoEnrichment  (plugin-sourced shadow data)
  video_id    → Video
  plugin_id   → MetadataPlugin
  field_key   string
  field_value string
  fetched_at  timestamp
```

## Open Questions (Phase 3 Specific)

1. **Tag graph cycles**: Should the system enforce DAG constraints (no cycles) or allow and detect cycles at query time?
2. **People config schema**: Should extra metadata fields be defined globally (all people share the schema) or per-person? Global is simpler; per-person is more flexible.
3. **TMDB/IMDB API rate limits**: Should the plugin system implement a request queue/rate limiter, or delegate that to the plugin implementation?
4. **Writeback atomicity**: What happens if ffmpeg crashes mid-write? Is the backup strategy sufficient, or is a staging-then-rename approach needed?
5. **Preview storage size**: 20-second previews at 1 Mbps = ~2.5 MB each. For a 10k-video library that's 25 GB. Should there be a storage budget or auto-pruning policy?
