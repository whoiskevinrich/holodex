# Phase 2 Spec: MCP Server + UI Polish

**Status**: Draft  
**Phase**: 2 of 3  
**Depends on**: Phase 1 complete; ADR-005 (MCP transport), ADR-009 (Thumbnail strategy), ADR-013 (Metadata field mapping)

---

## Objective

Expose the full library query capability via a Model Context Protocol (MCP) server, add thumbnail generation, and polish the browse experience with sort controls, keyboard navigation, and a "Recently Added" shelf.

---

## Scope

### In Scope
- MCP server with 4 tools (search_videos, get_video, list_people, list_tags)
- Background thumbnail generation via ffmpeg
- Sort controls on browse view
- Codec/container detail on video detail page
- Keyboard navigation
- Responsive mobile layout
- Recently Added shelf on home page
- Prometheus metrics endpoint
- Bulk re-scan endpoint
- Configurable metadata field mapping (display + filterable facets)

### Out of Scope (Phase 2)
- People aliases / enrichment (Phase 3)
- Tag graphs / aliases (Phase 3)
- Metadata source plugins (Phase 3)
- Metadata writeback (Phase 3)
- Autogenerated preview trailers (Phase 3)

## Functional Requirements

### F10: MCP Server

**Status: implemented (2026-06-13).** Built on `mark3labs/mcp-go` (ADR-005) in `internal/mcp`, sharing the same `*repo.Repo` as the REST API. The four tools (`search_videos`, `get_video`, `list_people`, `list_tags`) are read-only and return the spec's JSON schemas as tool text. `search_videos` resolves people/tag **names** to ids (an unknown name yields an empty result under AND semantics) and reuses the shared `VideoFilter` (with new `DateFrom`/`DateTo`). Transports: stdio via the `holodex -mcp-transport stdio` entrypoint (logs forced to stderr so stdout stays a clean JSON-RPC pipe), and Streamable HTTP at `/mcp` plus legacy SSE at `/mcp/sse` on `MCPPort`, started in-process when `MCP_ENABLED=true` and transport is `http`/`both`. Verified end-to-end over both transports (initialize → tools/list → tools/call).

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F10.1 | MCP server runs as part of the same Docker service, toggled via `MCP_ENABLED=true` env var | Setting env var starts MCP listener; absence skips it |
| F10.2 | `search_videos` tool: accepts `query` (title substring), `people` (array), `tags` (array), `duration_min` (seconds), `duration_max`, `resolution` (SD/HD/FHD/4K), `date_from` (ISO date), `date_to`, `page`, `page_size`; returns array of video objects + pagination | Claude Desktop can call this tool and receive results |
| F10.3 | `get_video` tool: accepts `id`; returns full video metadata object including file path, all people, all tags, technical metadata | Returns 404-equivalent error for unknown ID |
| F10.4 | `list_people` tool: accepts optional `query` (name substring), `sort` (name/count); returns array of `{id, name, video_count}` | Returns all people when no query provided |
| F10.5 | `list_tags` tool: accepts optional `query` (name substring), `sort` (name/count); returns array of `{id, name, video_count}` | Returns all tags when no query provided |
| F10.6 | MCP transport: stdio for local desktop use | Claude Desktop config with `command: docker exec -i holodex mcp` works |
| F10.7 | MCP transport: HTTP/SSE on `MCP_PORT` (default 7801) for networked clients | curl to `/mcp/sse` establishes SSE connection |
| F10.8 | MCP server shares the same database/index as the web server; no duplication | Changes from scanner appear in both web and MCP queries |

### F11: Thumbnail Generation

See ADR-009 for the full tiered strategy (embedded art at index time, throttled priority-aware background generation, eager-but-configurable backfill). **Status: implemented (2026-06-11).** Note: although ADR-009 framed Tier 1 as a Phase-1 deliverable, it was not built then — **all three tiers (embedded art, generated frames, priority bump) shipped together in Phase 2** (see the ADR-009 implementation-status note). F11.8's `holodex_thumbnail_queue_depth` is exposed as `thumbnail_queue_depth` on `GET /api/v1/admin/status` **and** (as of F13, below) as a pull-based gauge on `GET /metrics`.

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F11.1 | Background worker pool uses ffmpeg to extract a frame at `THUMBNAIL_SEEK_PERCENT` (default 10%) of video duration for files with no embedded cover art | Files without cover art get a generated thumbnail after background job completes |
| F11.2 | Thumbnails stored on disk at `DATABASE_PATH/thumbnails/:video_id.jpg`, served with HTTP cache headers | Thumbnail file exists on disk; repeat loads hit browser cache |
| F11.3 | Generation is non-blocking and throttled by `THUMBNAIL_WORKERS` (default 2) at low process priority (`THUMBNAIL_NICE`); new files are indexed immediately, thumbnail appears when ready | Browse grid shows a placeholder card until thumbnail is ready, then updates; host CPU load is bounded by worker count |
| F11.4 | Currently-visible items lacking a thumbnail are prioritized to the front of the generation queue | Opening a filtered view generates its visible items' thumbnails before continuing bulk backfill |
| F11.5 | Backfill posture configurable via `THUMBNAIL_BACKFILL` (default `eager`; `lazy` generates only for viewed items) | In `lazy` mode, un-viewed files never trigger background generation |
| F11.6 | Thumbnail regeneration can be triggered per-video via `POST /api/v1/media/:id/thumbnail` | API call triggers re-extraction |
| F11.7 | `THUMBNAIL_ENABLED` env var (default: `true`) disables Tier 2/3 generation for environments without ffmpeg or constrained hosts | Service starts and functions normally when set to `false`; embedded-art thumbnails still show |
| F11.8 | `holodex_thumbnail_queue_depth` exposed in Prometheus metrics | Metric reflects pending generation jobs |

### F12: Browse UI Polish

**Status: implemented (2026-06-13).** Sort is a `?sort=` param on `GET /media` backed by a whitelisted `ORDER BY` (repo.VideoFilter.orderBy); the frontend `SortDropdown` syncs it through the shared `filtersToParams` URL serializer (default `added_desc` omitted to keep `/` pristine). The Recently Added shelf (`RecentlyAddedShelf`) fetches the 20 newest independently and shows on the unfiltered landing view. Codec/audio-codec/bitrate/container come from ffprobe stream+format metadata (migration 0003 adds the columns; existing rows backfill on the next scan / admin rescan) and render on the detail page. Keyboard nav (`/` focus search, arrow-key grid roving, Enter via native anchors, Escape clears filters) is a window listener on the browse page. The grid reflows 1→2 cols at 480px and stays 2-up through ≤768px. Verified across all three skins.

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F12.1 | Sort controls: Title A-Z, Title Z-A, Date Added (newest/oldest), Duration (longest/shortest), Resolution (highest/lowest) | Changing sort updates grid without full reload |
| F12.2 | Active sort reflected in URL | Shareable URL preserves sort state |
| F12.3 | "Recently Added" horizontal shelf on home page showing 20 most recently indexed videos | Shelf appears above the main grid on `/`; each card is clickable |
| F12.4 | Codec/container detail on video detail page: video codec, audio codec, bitrate, container format | Populated from ffprobe/mediainfo stream metadata |
| F12.5 | Keyboard navigation: `/` focuses search bar; Tab/arrow keys navigate grid; Enter opens detail; Escape clears filters | Verified without mouse interaction |
| F12.6 | Responsive layout: browse grid reflows to 2 columns on viewport ≤ 768px, 1 column on ≤ 480px | Tested in browser at 375px width |

### F13: Observability

**Status: implemented (2026-06-13).** `/metrics` is a dependency-free hand-rolled Prometheus exposition (ADR-026); the queue-depth gauge is pulled live from the thumbnail pipeline at scrape time, while scan/search durations and the indexed-files counter are pushed via nil-safe `SetMetrics` seams on the scanner and handlers. The admin re-scan (F13.3) drives the scanner's `TriggerRescan`, which deduplicates concurrent triggers via the existing scan mutex and runs against the server-lifetime context.

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F13.1 | Prometheus metrics at `GET /metrics` | Endpoint returns valid Prometheus exposition format |
| F13.2 | Metrics exposed: `holodex_indexed_files_total`, `holodex_scan_duration_seconds` (histogram), `holodex_search_duration_seconds` (histogram), `holodex_thumbnail_queue_depth` | All metrics present in `/metrics` output |
| F13.3 | Admin re-scan: `POST /api/v1/admin/rescan` triggers full library re-index | Returns 202 Accepted; scan completes asynchronously |

### F20: Configurable Metadata Field Mapping

Maps one or more raw file tag keys to a single canonical Holodex field with a user-defined display label (e.g. `[Publisher, Label, Studio] → "Studio"`). Extended metadata is already captured at index time in Phase 1 (F2.9), so enabling or changing mappings requires no re-scan. See ADR-013 for the full design.

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F20.1 | Load field mappings from `metadata-mappings.yaml` mounted into the container | Adding a `studio` mapping makes the field available after restart (or config reload) without re-scanning |
| F20.2 | Many-to-one normalization: multiple source keys collapse into one canonical field; `sources` list order defines precedence | A file with both `Publisher` and `Studio` tags resolves the value from whichever key appears first in `sources` |
| F20.3 | Mapped fields render on the video detail page under their configured `label` | A file's `Publisher` tag displays as "Studio" with its value |
| F20.4 | Mapped fields with `filterable: true` become filter facets alongside People/Tags | Selecting a Studio value filters the browse grid to matching videos |
| F20.5 | Filterable mapped fields are exposed as query params on `GET /api/v1/media` (e.g. `?studio=Acme`) | API filters correctly by the mapped field |
| F20.6 | Filterable mapped fields are exposed as optional parameters on the MCP `search_videos` tool | MCP query by a mapped field returns correct results, consistent with the web UI |
| F20.7 | `multi: true` fields aggregate/split multiple values (e.g. multiple directors) | A file with two directors surfaces both as distinct values |
| F20.8 | Facet value lists are cached and invalidated on re-index (ADR-008) | Repeat facet loads are served from cache |
| F20.9 | A library-wide "metadata keys" view lists all distinct source keys with occurrence counts and sample values, flagging which are already mapped (mapping authoring aid, ADR-013) | View shows `Publisher` appears in N files with sample values, marked unmapped until a mapping is added |
| F20.10 | Mapping config changes apply via **both** an explicit reload endpoint (`POST /api/v1/admin/reload-config`) **and** container restart | Editing `metadata-mappings.yaml` and calling the reload endpoint updates fields without a restart |

## Open Questions (Phase 2 Specific)

1. **MCP authentication**: Should the HTTP/SSE MCP endpoint require a bearer token configurable via env var? Lean toward yes for networked use.
2. ~~**Thumbnail storage**~~: **Resolved (ADR-009)** — thumbnails stored on disk at `DATABASE_PATH/thumbnails/`, served with HTTP cache headers.
3. ~~**ffmpeg availability**~~: **Resolved (ADR-004/ADR-007)** — ffmpeg (with ffprobe) is bundled in the image; it is required for metadata extraction and thumbnails.
4. ~~**Mapping config reload (F20)**~~: **Resolved** — **both**: an explicit `POST /api/v1/admin/reload-config` endpoint **and** restart support (F20.10).
